# Issues #454, #456, #457, #459: Verification Slices

This document records the additive slices that make four hard-contributor
workflows observable and testable. Each slice preserves the existing contracts:
no export envelope, idempotency store, health report, or accessibility helper
changed shape. Everything here can be removed without affecting a caller that
does not import it.

Run all four executable verifications with:

```bash
npm run verify:issues-454-456-457-459
```

The targeted unit suites are:

```bash
npx vitest run core/health/__tests__/critical-workflow-coverage.test.ts
npx vitest run core/idempotency/__tests__/duplicate-submission.test.ts core/idempotency/__tests__/concurrency.test.ts
npx vitest run core/export/__tests__/field-authorization-receipt.test.ts
npx vitest run core/testing/__tests__/keyboard-async-coverage.test.ts
```

## Issue #454 — Synthetic monitoring for critical workflows

### What was added

`core/health/critical-workflow-coverage.ts` is a pure coverage ledger over the
existing journey catalogue (`journeys.ts`) and workflow monitor (#410). The
monitor answers "is the workflow up?"; coverage answers the different question
"have all four operational paths actually been exercised?".

Every journey in `JOURNEY_IDS` must have passing evidence for `normal`,
`failure`, `retry`, and `authorization`. `evaluateWorkflowCoverage` derives a
versioned report from evidence; `runWorkflowCoverage` executes injected checks
with bounded retries, isolates a check that throws, and checks `admin:health`
before any check runs.

### Paths covered

| Path | Coverage |
|---|---|
| Normal | Full evidence yields `ready`, `criticalReady`, 100% coverage |
| Failure | Missing critical evidence blocks both flags; a non-critical gap only blocks `ready` |
| Retry | The last evidence item for a scenario wins; runner retries a transient failure up to `maxAttempts` |
| Authorization | A viewer is refused with `synthetic_unauthorized` and no check executes |

### Edge cases and recovery/rollback

- A check that throws becomes `check_crashed` evidence and cannot abort other
  checks; journeys are evaluated sequentially so a run never bursts the probe
  rate limit.
- `maxAttempts` is clamped to 1–5; a malformed outcome is treated as a failure,
  never as a pass.
- Evidence is supplied by the caller. Dropping the new module returns the
  system to the exact #410 behavior — this is the rollback path.
- `WORKFLOW_COVERAGE_VERSION = 1` is part of the report. A breaking report
  change must bump the version; old reports stay readable because no consumer
  parses them today.

## Issue #456 — Duplicate-submission concurrency coverage

### What was added

`core/idempotency/duplicate-submission.ts` is an actor-aware boundary around
`withIdempotency`. The store remains unchanged and still guarantees that a
claimed key runs once. The new wrapper:

- authorizes before a key is claimed (`maintainer`, `service`, or an explicit
  `ops:submit` grant);
- fires N logically identical attempts and reports executions, replays,
  in-flight rejections, conflicts, and failures separately;
- covers the recovery path with a derived `:retry` key, because a recorded
  failure is intentionally replayed on the original key.

The stale `core/idempotency/__tests__/concurrency.test.ts` was rewritten
against the real store API (`begin`/`complete`/`fail`/`abandon` and
`withIdempotency`). It previously called a nonexistent `store.record()`, so the
concurrency suite could not run at all.

### Paths covered

| Path | Coverage |
|---|---|
| Normal | Concurrent copies execute once; a later attempt replays the recorded value |
| Failure | A recorded failure replays its error code instead of re-running the side effect |
| Retry | `runDuplicateSubmissionRetry` executes the recovery once on a new key |
| Authorization | An unprivileged actor consumes no key; an explicit grant succeeds; differing owners still conflict |

### Edge cases and recovery/rollback

- Guarantees are scoped to one JS realm (the store's `begin` claim is
  synchronous). Cross-process exactly-once still requires atomic CAS storage as
  documented in `CONCURRENCY.md`; this slice does not claim otherwise.
- `concurrency` is clamped to 1–64. A thrown side effect is reported as
  `duplicate_submission_crashed` and recorded as a failure by the store.
- There is no rollback of a completed side effect: a duplicate never starts a
  second one. Recovery is a new, separately keyed attempt. A stuck claim can be
  released with `store.abandon(key)` by the existing idempotency API.
- Removing the wrapper leaves `withIdempotency` and the worker queue untouched.

## Issue #457 — Privacy-safe export with field-level authorization

### What was added

`core/export/field-authorization-receipt.ts` produces a decision receipt for a
field-level export request. `exporter.ts` redacts but cannot explain a decision;
`permission-export.ts` decides but does not persist a proof. The receipt fills
that gap and never stores a field value.

Decisions are derived with the **exporter's own rule semantics**: combined
defaults plus request rules, first match wins, only a `maintainer` bypasses a
rule, and a denial masks only when `onDenied: "mask"` (exporter emits
`[FILTERED: UNAUTHORIZED]`). A receipt therefore cannot claim `allow` where the
export would redact. `receiptId` hashes the full authorization context but no
wall-clock values, so retries agree on identity; injecting `now` also keeps the
digest byte-identical.

### Paths covered

| Path | Coverage |
|---|---|
| Normal | Sorted `allow`/`omit`/`mask` decisions; digest verifies; decisions match `applyFieldLevelAuthorization` |
| Failure | Duplicate/blank fields, invalid key, unsupported schema, non-positive TTL, out-of-scope actor, and tampering are refused |
| Retry | Same key/context yields the same receipt id; the same injected clock yields the same digest |
| Authorization | Owners, maintainers and services with `export:audit` see reasons; everyone else gets a sanitized view with no actor id; revocation is owner/auditor only |

### Edge cases and recovery/rollback

- `onDenied: "error"` is reported as `omit` because that is what the export
  boundary actually emits; `FieldAction` still accepts `error` for older
  receipts.
- Schema version must equal `EXPORT_CURRENT_SCHEMA_VERSION`. After a breaking
  redaction change, bump the export schema in the same commit as the contract
  drift test; old artifacts then fail as `schema_unsupported`.
- `revoked` is excluded from the digest: revocation is advisory disclosure
  control, not a persisted deny-list. Callers needing authoritative revocation
  must persist the flag and check it before disclosure.
- Recovery is discard-and-regenerate: exports are derived artifacts, so a bad
  rule set is reverted, a new receipt key is used, and `expiresAt` retires the
  old artifact. No source record is mutated.
- `service` actors remain unable to request `maintainer` scope, matching
  `authorizeExport`; `export:audit` only grants receipt disclosure, not export
  scope.

## Issue #459 — Keyboard and async status accessibility coverage

### What was added

`core/testing/keyboard-async-coverage.ts` is a DOM-free coverage ledger for
keyboard and async-status observations. It can be driven from Vitest, a
Playwright reporter, or the verifier above. Expectations are read from the
shipped `core/ui/accessibility.ts` helpers (`getStatusAnnouncement`,
`getStatusLivePoliteness`, `getStatusAriaAttributes`) so a helper change cannot
silently invalidate a test.

### Paths covered

| Path | Coverage |
|---|---|
| Normal | All four paths pass when focus order, activation, focus return, announcement, politeness, role and busy match the helpers |
| Failure | A wrong announcement or a non-alert error role produces typed issues |
| Retry | The `loading → error → success` status sequence is required, not just one status |
| Authorization | Missing keyboard evidence and non-assertive authorization errors are reported |

### Edge cases and recovery/rollback

- Empty focus order is a failure (`keyboard_no_focusable_controls`), so a test
  cannot pass vacuously.
- Errors must be assertive and set `role="alert"`; loading must set
  `aria-busy`. Each mismatch is reported independently.
- The evaluator is additive and has no side effects. Removing it returns the
  existing hooks, components, and E2E keyboard suite to their prior behavior.
- When a helper's contract legitimately changes, update `accessibility.ts`
  first and let the evaluator derive the new expectation; no expectation is
  duplicated in the ledger.

## Contract and migration plan

| Slice | Contract impact | Migration |
|---|---|---|
| #454 | New versioned report; no existing health report changed | Optional import; bump `WORKFLOW_COVERAGE_VERSION` on a breaking report change |
| #456 | New actor-aware wrapper; idempotency store API unchanged | Rewrite of the stale `concurrency.test.ts` only; no persisted data changes |
| #457 | New receipt type; export envelope untouched | Reject unsupported schema versions; reissue receipts with a new key after a rule change |
| #459 | New evaluator; no hook or component API changed | None — consumers opt in by feeding observations |

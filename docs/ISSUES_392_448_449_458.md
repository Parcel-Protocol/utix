## Issue #392 — Worst-case load tests and resource budgets

### What was added

`core/testing/load-budget.ts`:

- `runLoad(op, { iterations, concurrency }, retry?)` drives an operation and
  reports `p50Ms`, `p95Ms`, `maxMs`, `errors`, `errorRate`, `retries` and
  `heapGrowthBytes`. A call fails when it throws or returns `{ ok: false }`.
  Thrown errors may be retried (`maxAttempts`, `isRetryable`); `Result`
  errors are expected outcomes and never retried.
- `checkBudget(report, budget)` returns the report, or `budget_exceeded` with
  every violated limit (p95, error rate, heap growth, retries).

Synchronous operations are timed up to their return, not across the `await`,
so queueing behind other workers is never billed to a call.

### Coverage

| Path | Test |
| --- | --- |
| Normal | 300 propose+accept cycles; 20k flag evaluations with every guardrail; audit append on a 2,000-event trail |
| Failure | Injected storage burst breaches the error budget; latency breach; invalid profile |
| Retry | Transient timeouts absorbed by retries and counted against `maxRetries`; non-retryable faults never retried; 1,000 idempotent replays create one proposal |
| Authorization | 5,000 unauthorized proposals rejected cheaply with no state change; emergency-disabled flag short-circuits under load |

### Finding fixed: audit writes were O(n²)

The load tests showed `recordAudit` re-reading, re-parsing, **re-redacting** and
re-serializing the whole trail on every write (400 ownership proposals took
4.9s). `core/audit/audit.ts` now:

- redacts only the new event (stored events were redacted when written);
- keeps a parsed view keyed by the exact raw string, so a write from elsewhere
  (another tab, `reset`) forces a re-parse;
- appends to a clean trail in place by concatenating onto the cached blob
  prefix (no slice, so the blob is never copied in JS); anything not clean
  (unparseable, entries failing `isEvent`) falls back to the full rewrite.

The stored JSON is byte-compatible with before. 800 writes: 9.0s → ~0.2s.

### Finding fixed: ledger append was O(chain)

Every audit event also commits to the hash-chained ledger, whose `append`
re-parsed and re-serialized the whole chain. A sweep expiring 500 proposals at
once took ~2.5s. `core/ledger/ledger.ts` `append` now has a fast path:

- The instance remembers the exact blob it last wrote, the blob minus its
  closing `]}`, and its tail entry as JSON.
- If storage still holds exactly that blob, the new entry is concatenated on.
  The result is byte-identical to `JSON.stringify` of the full state (tested).
- Any other write (`prune`, `reseal`, `reset`, another instance or tab, a
  tampered or unparseable blob) changes the raw string, so the original full
  read runs, including `ledger_broken` for an unparseable blob.
- The head-hash check still runs on every append, so editing the stored tail
  is still refused. The tail is cached as JSON, so a caller mutating a returned
  entry cannot alter it.

Append p95 at a 6,000-entry chain: 15.4ms → 0.16ms. The 500-proposal sweep:
~2.5s → ~0.4s under jsdom (budget 1.5s, to absorb CI contention). `prune`, `verify`,
`entries`, `export` and `reseal` are unchanged.

Storage-level ceiling: `localStorage.setItem` still copies the whole blob on
each write in a real browser. That cost is native memcpy, not JSON work. Removing
it would mean a chunked storage format, which needs a migration and is out of
scope here.

## Issue #448 — Rare-failure fixture generator

`core/testing/rare-failure-fixtures.ts` turns a seed into fault schedules for
the existing `FailureInjectionEngine`:

- `nth_attempt` — one fault on exactly attempt N (2..`maxAttempt`).
- `burst` — K consecutive faults (2..`maxBurst`), then recovery.
- `compound` — faults on two different steps of the same workflow.

Guarantees and edge cases:

- **Deterministic**: mulberry32 PRNG; same seed → identical fixtures. Rules
  never use `probability`, which would call `Math.random()` at evaluation time.
- **Coverage**: a 200-seed corpus covers every `FaultType` and every kind.
- Single-step workflows never get `compound` fixtures; an empty step list throws.
- **Authorization**: `installRareFailureFixture` requires an `AuthContext`
  (the engine's own `registerRule` treats a missing one as allowed).
- **Rollback**: installation is all-or-nothing. If any rule is refused, rules
  already registered are unregistered. The returned function uninstalls.

## Issue #449 — Ownership transfer acceptance and expiry

Acceptance, expiry (lazy and swept), authorization and idempotency already
existed (#405). The gap was **retry after a failure**:

`initiate`/`accept` claimed an idempotency key and then returned validation
errors (`transfer_expired`, `unauthorized_not_recipient`,
`transfer_active_conflict`, ...) without releasing it. Every retry with the same
key then got `idempotency_in_flight` for the key's 24h TTL instead of the real
outcome, and a stranger's failed attempt could block the rightful recipient.

Fix: a claim taken by the call is released (`abandon`) on any post-claim error.
A claim refused by `begin` itself is never released, so a concurrent caller's
in-flight claim is untouched. Released keys re-run from scratch, so a retry sees
current state: an expired transfer keeps reporting `transfer_expired`, and a
proposal blocked by a conflict succeeds once the conflict is swept.

Edge cases tested: the expiry deadline is exclusive (accept at exactly
`expiresAt` is rejected); a successful accept replays from its key even after the
proposal's deadline, with the original `settledAt` and no duplicate audit entry.

## Issue #458 — Feature rollout guard and emergency disablement

The rollout guard, circuit breaker and kill switches already existed (#223,
#273). The gap was that `triggerEmergencyDisable`/`clearEmergencyDisable` carry
no authorization. They stay unchanged (the automated guard uses them).
Operator paths now use new wrappers in `core/feature-flags/rollout-guard.ts`:

- `authorizedEmergencyDisable(flag, auth, { reason })` requires
  `admin:config` or `admin:recovery` (maintainers) and a non-blank reason.
  Returns `permission_denied` / `reason_required` otherwise.
- **Retry-safe**: disabling an already-disabled flag returns the original record
  with `alreadyActive: true`, so a retry never rewrites who triggered it or when.
- `authorizedClearEmergencyDisable(flag, auth)` is the rollback path; clearing a
  flag that is not disabled succeeds and returns `false`.
- Every attempt, allowed or denied, is audited (`admin.config_changed`).
- `getEmergencyDisableRecord(flag)` (flags.ts) exposes the active record.

Recovery semantics: an operator clear re-enables the flag, but a `RolloutGuard`
that has tripped stays closed; recovery from a guard trip means replacing the
guard, as before.

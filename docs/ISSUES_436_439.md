# Issues #436–#439: Operational Resilience, Resource Budgets, and Replay Safety

This document describes the design, implementation, operational paths, edge cases, recovery/rollback behavior, and contract preservation for the four issues resolved in this batch:
- **Issue #436**: Create worst-case load tests and resource budgets
- **Issue #437**: Implement cancellation and cleanup for long operations
- **Issue #438**: Add durable checkpoints around external side effects
- **Issue #439**: Build versioned event replay for derived projections

## Issue #436 — Create Worst-Case Load Tests and Resource Budgets

### What was added
- **Core Budget & Load Engine**: [`core/quota/worst-case-load.ts`](file:///Users/heqmah/utix/core/quota/worst-case-load.ts)
  - `evaluateResourceBudget`: In-flight concurrency evaluation, load-shedding detection, and per-request cost bounds checking.
  - `runWorstCaseLoadTest`: Simulated multi-actor worst-case traffic generator measuring peak concurrency, shed rates, resource saturation, and quota isolation across actors.
  - `grantEmergencyBudgetOverride`: Authorized temporary limit overrides for operational mitigation during traffic spikes.
  - Constants: `DEFAULT_RESOURCE_BUDGET_PROFILE` covering compute, storage, external API, and indexing limits.
- **Unit & Property Tests**: [`core/quota/__tests__/worst-case-load.test.ts`](file:///Users/heqmah/utix/core/quota/__tests__/worst-case-load.test.ts)
- **Exports**: Exported through [`core/quota/index.ts`](file:///Users/heqmah/utix/core/quota/index.ts).

### Operational Paths Covered

| Path | Description |
|---|---|
| **Normal** | Moderate concurrent loads across operations succeed within budget limits without shedding or exhaustion. |
| **Failure** | Over-budget requests, costs exceeding `maxCostPerRequest`, negative costs, or concurrency saturating `maxConcurrentInFlight` fail deterministically with `quota_invalid_cost`, `quota_exceeded`, or `concurrency_limit_exceeded`. |
| **Retry & Isolation** | Noisy-neighbor isolation ensures that an abusive actor exhausting their principal quota is throttled without starving innocent concurrent actors. Retries succeed once window resets. |
| **Authorization** | `grantEmergencyBudgetOverride` requires `admin:quota` permission or `maintainer` role. Unauthorized actors (`viewer`, `service`, `user`) are denied with `quota_override_denied`. |

### Edge Cases and Error Codes
- `quota_invalid_cost`: Cost is negative, zero, non-integer, or exceeds `maxCostPerRequest`.
- `concurrency_limit_exceeded`: System-wide in-flight requests meet or exceed `maxConcurrentInFlight`.
- `quota_unknown_operation`: Requested operation is unmapped in the quota policy table.
- `quota_override_denied`: Attempt to grant emergency override without maintainer privileges.
- Reason sanitization: Overrides sanitize operational reasons to lowercase alphanumeric slugs conforming to `REASON_PATTERN` (`/^[a-z0-9_.:-]{1,64}$/`).

### Recovery and Rollback Behavior
- **Load Shedding**: High load past `shedThresholdPercent` (e.g. 80%) flags requests as shed to allow graceful service degradation rather than unhandled crash.
- **Emergency Mitigation**: Maintainers can deploy an override with bounded TTL (up to 7 days) to elevate limits for critical accounts during high-profile ticket sales. Overrides can be revoked or expire automatically.

### Contract Preservation
- Preserves all existing `QuotaStore`, `QuotaStorage`, and `QUOTA_POLICIES` contracts without breaking changes.

## Issue #437 — Implement Cancellation and Cleanup for Long Operations

### What was added
- **Cancellation & Cleanup Engine**: [`core/operations/cancellation.ts`](file:///Users/heqmah/utix/core/operations/cancellation.ts)
  - `createOperationCancellationManager`: Manages operation lifecycles (`pending` -> `running` -> `cancelling` -> `cancelled` / `completed` / `failed`).
  - LIFO Cleanup Registration: `registerCleanupHook` registers compensation/cleanup actions that execute in reverse order upon cancellation or failure.
  - Abort Signal Integration: Generates standard `AbortSignal` with timeout support to interrupt cooperative async workers.
  - Authorization Helpers: `cancelOperationAuthorized` and `retryOperationCleanup` ensuring caller identity and RBAC checks.
- **Unit Tests**: [`core/operations/__tests__/cancellation.test.ts`](file:///Users/heqmah/utix/core/operations/__tests__/cancellation.test.ts)
- **Exports**: Exported through [`core/operations/index.ts`](file:///Users/heqmah/utix/core/operations/index.ts).

### Operational Paths Covered

| Path | Description |
|---|---|
| **Normal** | Cooperative long-running task completes and is marked `completed`. Registered cleanups are cleared. |
| **Failure** | Task aborts or encounters error; cleanup hooks execute in strict LIFO order. If a cleanup hook throws, error is captured in `cleanupErrors` and status resolves to `cancelled` with error tracking. |
| **Retry** | `retryOperationCleanup` allows retrying remaining failed cleanup hooks without re-running successfully completed ones. |
| **Authorization** | Maintainers can cancel any operation; actors can cancel their own operations. Unrelated third parties (`viewer`) are denied with `permission_denied`. |

### Edge Cases and Error Codes
- `operation_not_found`: Referenced operation ID does not exist in the cancellation store.
- `operation_already_terminal`: Operation is already in `completed` or `failed` state and cannot be cancelled.
- `permission_denied`: Actor attempting cancellation is neither the operation owner nor a maintainer.
- `cleanup_in_progress`: Concurrent cancellation invocations against an operation currently in `cancelling` phase are rejected.

### Recovery and Rollback Behavior
- **Idempotent LIFO Cleanups**: Cleanup tasks (e.g., releasing temporary reservations, reverting intermediate ledger holds, pruning staging files) run in reverse order.
- **Failure Resilience**: Uncaught errors in individual cleanup hooks do not abort subsequent hooks. Failed hooks are recorded with error messages and can be retried via `retryOperationCleanup`.

### Contract Preservation
- Zero mutations to existing public interfaces; new utilities integrate cleanly into worker tasks and long-running batch jobs.

## Issue #438 — Add Durable Checkpoints Around External Side Effects

### What was added
- **Durable Checkpoint Engine**: [`core/operations/durable-checkpoints.ts`](file:///Users/heqmah/utix/core/operations/durable-checkpoints.ts)
  - 2-Phase Checkpointing: Records a durable `intent` before invoking external mutations (e.g. Horizon transaction submission, payment gateway call) and a `receipt` upon confirmation.
  - Ambiguous In-Doubt Handling: Distinguishes between definitive external failures (e.g., HTTP 400 Bad Request / account unfunded) and ambiguous failures (network timeout, connection reset, 504 Gateway Timeout).
  - Out-of-band Reconciliation: In-doubt operations mark `sideEffectCommitted: true` and transition to `in_doubt`, blocking automatic retries until authorized maintainer reconciliation.
  - Authorization Helpers: `resolveInDoubtCheckpointAuthorized` allowing maintainers to apply manual verification receipts or cancel abandoned in-doubt intents.
- **Unit Tests**: [`core/operations/__tests__/durable-checkpoints.test.ts`](file:///Users/heqmah/utix/core/operations/__tests__/durable-checkpoints.test.ts)
- **Exports**: Exported through [`core/operations/index.ts`](file:///Users/heqmah/utix/core/operations/index.ts).

### Operational Paths Covered

| Path | Description |
|---|---|
| **Normal** | Step records intent (`intent_logged`), executes external side effect, stores external receipt, and transitions to `committed`. |
| **Failure** | Definitive failure transitions checkpoint to `failed` and allows safe retry without side-effect collision. Ambiguous timeout transitions checkpoint to `in_doubt`. |
| **Retry** | Re-executing an already-committed idempotent step returns stored receipt immediately without re-invoking the external action. Blind retries while `in_doubt` are rejected with `external_effect_in_doubt`. |
| **Authorization** | `resolveInDoubtCheckpointAuthorized` allows maintainers to confirm or fail in-doubt transactions. Non-maintainers are rejected with `permission_denied`. |

### Edge Cases and Error Codes
- `external_effect_in_doubt`: Side-effect execution timed out or crashed without confirmation; manual or reconciliation verification required before any retry.
- `external_effect_failed`: External effect failed definitively and is confirmed not applied.
- `checkpoint_not_found`: Referenced checkpoint ID does not exist.
- `checkpoint_not_in_doubt`: Attempting to resolve a checkpoint that is not in `in_doubt` phase.
- `permission_denied`: Attempting manual resolution without `maintainer` role or `admin:reconcile` permission.

### Recovery and Rollback Behavior
- **Ambiguous Timeout In-Doubt Protocol**: When an RPC call drops, the system cannot know if Stellar or the bank processed the transaction. Instead of retrying (which risks double-spending or duplicate minting) or failing (which causes ledger drift), the checkpoint freezes into `in_doubt`.
- **Maintainer Reconciliation**: Maintainers inspect block explorers or external gateway receipts, then call `resolveInDoubtCheckpointAuthorized` with `outcome: "applied"` (attaching transaction hash) or `outcome: "not_applied"` to safely unlock workflow resumption.

### Contract Preservation
- Standardizes side-effect safety without altering existing transport contracts or storage drivers.

## Issue #439 — Build Versioned Event Replay for Derived Projections

### What was added
- **Derived Projection Engine**: [`core/replay/derived-projections.ts`](file:///Users/heqmah/utix/core/replay/derived-projections.ts)
  - `buildDerivedProjection`: Runs versioned event replay using schema upcasters, invariant validations, and atomic slot promotion.
  - `buildDerivedProjectionAuthorized`: Authorization-wrapped projection rebuild checking `replay:projection` permission or `maintainer` role.
  - `rollbackDerivedProjection`: Points active reader pointer back to previous version slot instantaneously.
  - `rollbackDerivedProjectionAuthorized`: Permission-checked rollback workflow.
- **Unit Tests**: [`core/replay/__tests__/derived-projections.test.ts`](file:///Users/heqmah/utix/core/replay/__tests__/derived-projections.test.ts)
- **Exports**: Exported through [`core/replay/index.ts`](file:///Users/heqmah/utix/core/replay/index.ts).

### Operational Paths Covered

| Path | Description |
|---|---|
| **Normal** | Historical events replayed through registered upcasters, validated against specification invariants, staged into slot, and promoted atomically to active version. |
| **Failure** | Event sequence errors or domain invariant violations (e.g. negative balances, schema divergence) abort build with `validation_failed`, leaving active slot untouched. |
| **Retry & PIT** | Supports point-in-time rebuilding (`untilSequence`), dry-run evaluations (`dryRun: true`), and resuming from partial checkpoints (`mode: "resume"`). |
| **Authorization** | Replay and rollback require maintainer privileges (`replay:projection`). Viewers or unprivileged actors are rejected with `permission_denied`. |

### Edge Cases and Error Codes
- `validation_failed`: State invariant check failed after replaying events.
- `permission_denied`: Caller lacks `replay:projection` or maintainer credentials.
- `no_previous_version`: Attempting to roll back a projection that has no prior active version slot.
- `unsupported_event_version`: Event version encountered in stream has no registered upcaster path to target version.
- `replay_in_progress`: Another worker currently holds the distributed lock for the projection name.

### Recovery and Rollback Behavior
- **Zero-Downtime Atomic Swap**: Replays write state to staging version slots. Readers remain pinned to the active slot until validation passes and `setActive` flips the pointer.
- **Instantaneous Rollback**: If a newly promoted projection reveals unexpected regressions in production, `rollbackDerivedProjection` immediately restores readers to `previousVersion` in O(1) time without re-reading the event log.

### Contract Preservation
- Built directly on top of the established `ProjectionStore`, `replayProjection`, and `createUpcasterRegistry` interfaces without breaking existing projection definitions.

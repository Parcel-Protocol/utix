# Issues #450–#453: Deployment Safety and Fuzz Coverage

This document describes the implementation, edge cases, recovery procedures, and rollback
considerations for the four issues resolved in this batch.

---

## Issue #450 — Deployment Rollback Verification Checks

### What was added

Extended test coverage for the existing `core/recovery/rollback-verifier.ts` suite.
New test file: `core/recovery/__tests__/rollback-verification-checks.test.ts`.

### Paths covered

| Path | Description |
|---|---|
| Normal | Clean dataset with no rolled-back records passes all 6 checks in read-only mode |
| Normal | Empty dataset passes without error |
| Normal | Custom `now` clock correctly classifies a 1-hour-old transfer as fresh against the 24-hour window |
| Normal | Human-readable formatted report contains all expected sections |
| Failure | Ticket issued under `rolledBackFromVersion` detected as a critical violation |
| Failure | Pending transfer from rolled-back version flagged for cancellation |
| Failure | Transfer pending beyond `maxPendingTransferAgeMs` flagged as a warning |
| Failure | Unconfirmed redemption nonce triggers a critical repair record |
| Failure | Active worker jobs (`queued`, `running`, `retrying`) with rolled-back payload require dead-lettering |
| Failure | Event capacity overflow: active ticket count exceeds event capacity |
| Failure | Duplicate ticket IDs caught as critical violations |
| Failure | Orphaned ticket referencing a non-existent `eventId` flagged |
| Failure | Invalid Stellar owner public key on a ticket triggers a critical external-reference flag |
| Failure | Malformed external Stellar transaction hash (not 64 hex chars) triggers a warning |
| Failure | Fraud records raised under rolled-back version and still pending review are flagged |
| Failure | Formatted report contains `ROLLBACK REQUIRES ACTION [FAIL]` on critical failures |
| Retry | Repeated calls with identical inputs produce identical reports (deterministic) |
| Retry | Input dataset is never mutated across multiple runs |
| Retry | `readOnly` defaults to `true`; can be set to `false` explicitly |
| Retry | Custom `maxPendingTransferAgeMs` can widen or narrow the stale-transfer window |
| Edge | Cancelled tickets are excluded from capacity accounting |
| Edge | Fraud records with `isManualReviewPending: false` are ignored even if from rolled-back version |
| Edge | Non-pending transfers in any status are never flagged as stranded operations |
| Edge | Report `timestamp` reflects the custom `now` clock option |

### Recovery procedure

1. Run `node scripts/verify-release-rollback.mjs` after every rollback.
2. For each `requiresManualRepair: true` record, follow the `suggestedAction` field.
3. Rerun until the report shows `CLEAN ROLLBACK [PASS]`.
4. All verification checks are read-only; they never mutate any record.

## Issue #451 — Permission-Diff Preview Before Policy Changes

### What was added

Extended test coverage for `core/policy/permissionDiff.ts`.
New test file: `core/policy/__tests__/permission-diff-preview.test.ts`.

### Paths covered

| Path | Description |
|---|---|
| Normal | Benign additive change: `overallRiskLevel: "low"`, `recommendedAction: "proceed"` |
| Normal | `applyRolePolicyChange` captures an immutable rollback snapshot before applying changes |
| Normal | `reportId` and `generatedAt` are stable functions of the `now` clock |
| Normal | No-op diff: zero additions, zero removals, `overallRiskLevel: "low"` |
| Normal | Multiple simultaneous role changes: `affectedRolesCount` reflects only changed roles |
| Normal | Mixed escalation + revocation: both flags are set correctly |
| Failure | Critical escalation: `admin:recovery` to `viewer` → `critical`, `block`, `allowApply: false` |
| Failure | Critical escalation: `admin:replay` to `viewer` → gating reason recorded |
| Failure | Lockout risk: emptying `maintainer` permissions → `critical`, `LOCKOUT RISK` warning |
| Failure | High-privilege grant to `service` role produces at least `high` risk level |
| Failure | `applyRolePolicyChange` on a blocked diff returns `critical_escalation_blocked` |
| Failure | Unknown role in proposed mapping returns `invalid_role_definition` |
| Failure | Unknown permission string returns `invalid_permission` |
| Failure | Empty proposed mapping returns `empty_permissions` |
| Failure | Non-array permission value returns `invalid_role_definition` |
| Authorization | Viewer callers denied with `unauthorized` |
| Authorization | Service callers denied with `unauthorized` |
| Authorization | No caller option passes without an auth check |
| Authorization | Maintainer + `allowCriticalEscalations: true` bypasses the block gate |
| Retry | `retryDiffReport` succeeds after transient failures on earlier attempts |
| Retry | `retryDiffReport` returns `diff_retries_exhausted` after `maxRetries` failures |
| Retry | Identical inputs always produce identical risk level and warnings |
| Edge | Rollback snapshot is immutable: mutating `newPermissions` does not affect it |
| Edge | `netChange` is positive for net escalations, negative for net revocations |
| Edge | `netChange` is zero for a permission swap of equal count |
| Edge | `unchangedPermissions` correctly lists permissions present in both current and proposed |

### Recovery procedure

1. Always call `generateDiffReport` before any policy mutation.
2. If `recommendedAction` is `"block"`, do not proceed without an explicit override and manual sign-off.
3. Store `rollbackSnapshot` out-of-band; use `applyRolePolicyChange` with the snapshot to revert if needed.

## Issue #452 — Stable Problem-Details Error Taxonomy

### What was added

Extended contract and integration tests for `core/errors/problem-details.ts`.
New test file: `core/errors/__tests__/problem-details-taxonomy.test.ts`.

### Paths covered

| Path | Description |
|---|---|
| Normal | Every code in `PROBLEM_CODES` produces a valid RFC 7807 envelope (7 required fields) |
| Normal | `type` URI matches `https://utix.dev/problems/<code-with-hyphens>` exactly |
| Normal | `code` on the envelope always matches the registry key |
| Normal | Retryable transport codes (`horizon_rate_limited`, `rpc_timeout`, …) have `retryable: true` |
| Normal | Validation and client-error codes have `retryable: false` |
| Normal | `correlationId`, `instance`, `extensions`, and `overrideDetail` are propagated correctly |
| Normal | Default `detail` comes from the taxonomy, never from user input |
| Failure | Horizon bridge: all 7 `HorizonErrorCode` values produce valid envelopes |
| Failure | Horizon `rate_limited` → `retryable: true`; `not_found` → `retryable: false`, `status: 404` |
| Failure | Horizon bridge never echoes raw server error text in `detail` or `title` |
| Failure | RPC bridge: all standard JSON-RPC error codes produce valid envelopes |
| Failure | RPC transport `timeout` → `retryable: true`, `code: "rpc_timeout"` |
| Retry | `isProblemRetryable` is consistent with the registry `retryable` field |
| Retry | `problemDetailsFromCode` is idempotent: same code → same envelope shape |
| Contract | Every code in the `ProblemCode` union literal is present in `PROBLEM_CODES` |
| Contract | `PROBLEM_CODES` contains no undocumented extra codes |
| Contract | Type URIs contain no underscores (slugs use hyphens) |
| Contract | Validation codes have `status: 400`; not-found codes have `status: 404` |
| Contract | Server-error transport codes have `status: 503` or `504` |
| Edge | `extensions` object is not mutated by `problemDetailsFromCode` |
| Edge | Retryable codes are a subset of `status` values `{429, 500, 503, 504}` |
| Edge | Non-retryable codes all have `status >= 400` |

### Stability contract

- `code` values are **permanent**. Never rename or remove an entry. Add new codes to supersede old ones.
- `type` URIs are permanent and must resolve to this documentation.
- `hint` and `detail` text may be improved in wording but must remain semantically stable.
- `extensions` fields are additive; consumers must ignore unknown keys.

## Issue #453 — Fuzz Tests for Malformed and Boundary Inputs

### What was added

Extended property-based fuzz coverage for all core boundary surfaces.
New test file: `core/__tests__/fuzz-malformed-boundary.test.ts`.

### Properties verified

| Target | Property |
|---|---|
| `parseAmount` / `stroopsToAmount` / `amountToStroops` | Corpus of 20 boundary strings each produces a valid `BigInt` in `[INT64_MIN, INT64_MAX]` or a declared `AmountParseError`. 500 random strings from the boundary charset never throw. Every random `int64` round-trips exactly. |
| `parseJsonRpcResponse` | 18-entry corpus of malformed payloads never throws. Random deeply-nested arbitrary values always return `jsonrpc: "2.0"`, exactly one of `result`/`error`, and an integer `error.code`. |
| `problemDetailsFromCode` | Every code does not throw. Boundary `correlationId`, `overrideDetail`, and `extensions` values never throw. |
| `horizonToProblemDetails` / `rpcToProblemDetails` | 500 random calls across all error types never throw; `code` is always lowercase_snake and `retryable` is always boolean. |
| `hasPermission` / `hasAnyPermission` / `hasAllPermissions` | Unknown roles (including prototype keys, `null`, `undefined`) are denied without throwing. Known roles keep their exact declared grants. |
| `PermissionDiffEngine.generateDiffReport` | Boundary proposed inputs (`null`, `undefined`, `{}`, non-array permission) never throw. |
| `verifyReleaseRollback` | Empty dataset never throws. Boundary Stellar addresses and transaction hashes (empty, non-hex, wrong length) never throw. 50 randomly-sized datasets each produce a structurally valid 6-check report. A 1 000-ticket dataset passes cleanly when capacity is sufficient. |

### Reproducing a failure

```bash
FUZZ_SEED=<seed printed in the assertion message> npm test -- core/__tests__/fuzz-malformed-boundary
```

### Compatibility

All properties only constrain invariants (no throws, declared error codes, valid shapes).
No existing behaviour changes; no migration is needed.
